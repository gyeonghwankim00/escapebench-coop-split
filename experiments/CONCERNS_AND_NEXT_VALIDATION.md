# 협력형 방탈출에서 고민한 문제와 다음 검증

작성 기준: 2026-11-20. 현재 분할 v3, 실행 프로토콜 v7과 다운로드된 nightly-v6 결과 기준.

## 회의에서 먼저 설명할 핵심

> 원본 방탈출을 A/B 접근 구역으로 나누고, 한 모델이 양쪽을 제어하는 Solo와 두 에이전트가 각자의 구역에서 협력하는 Peer를 만들었다. 그런데 실험 실패에는 퍼즐 추론뿐 아니라 명령 형식, 기억 소실, 탐색 편중, 반복, 물건 소유권, 전달 비용이 함께 작용했다. 따라서 낮은 점수를 바로 협력 능력 부족으로 해석하기 어려웠다. 다음에는 강한 모델로 같은 입력과 환경을 시험해, 정상적인 탐색·행동·교환이 가능한지부터 확인하려 한다.

현재 확인한 것은 **실행 구조와 일부 정답 경로의 성립**이다. 실제 에이전트가 관측 가능한 단서를 따라 협력하며 해결하는 벤치마크로서의 타당성은 계속 검증해야 한다.

최신 44회 중 42회는 500환경 행동 예산 종료, 2회는 GPU OOM이다. 정상 종료 42회에서 탈출은 0회다. 이 결과만으로 환경 불가능·모델 추론 부족·협력 실패 중 하나를 원인으로 확정할 수 없다.

### 분할과 데이터의 타당성

| 고민 | 왜 중요했나 | 현재 상태와 남은 질문 |
|---|---|---|
| 원본을 너무 축약한 것 아닌가 | 쉬운 조각만 남기면 원본의 긴 탐색·도구 사용을 평가하지 못함 | 초기 축약 JSON에서 원본 YAML 엔진 기반으로 전환. 다만 객체를 보존해도 모든 원본 행동이 계속 필수인 것은 아님 |
| 수작업인가 규칙 기반인가 | 분할 근거와 재현 가능성이 필요함 | 초기 수작업 → 제약·점수 기반 후보 탐색 → 선택한 분할 고정. 단서 연결 주석에는 작성자의 해석이 들어감 |
| 진짜 두 방인가 | 복도와 그 안의 서랍 클로즈업을 서로 다른 역할에 주면 공간 설명이 부자연스러움 | 가능한 부모 장면·클로즈업 묶음. 현재는 여러 장면으로 이루어진 두 접근 구역 |
| 분할하면서 문제가 쉬워지지 않았나 | B를 잠긴 방 안에서 시작시키면 원래 진입 퍼즐을 건너뛸 수 있음 | 당구장에 우회가 있어 대조군으로 분리. 다른 문제도 필수 경로·시작 위치 영향 검토 필요 |
| 실제로 교환이 필요한가 | 양쪽이 각자 쉬운 행동만 해도 점수는 오를 수 있음 | 메시지/물건 교환 제거 검사를 했지만 참조 지식·무료 관측 등 낙관적 가정이 있음. 실제 비용 있는 경로와 사람 검증 필요 |
| 모든 단서가 반대편에 있어야 하나 | 제안서의 강한 전제와 실제 분할이 다름 | 일부 교차 의존과 방 안 퍼즐이 공존. 모든 단서 교차를 요구할지 팀 합의 필요 |
| 한쪽이 초반부터 막히지 않나 | 일방적 공급 의존을 협력 실패로 잘못 볼 수 있음 | 2-1, 2-2, 3-1, 3-2에서 B 초기 단독 진척이 낮음. 점수 진척이 없다는 것이 탐색할 곳도 없다는 뜻은 아님 |
| 원격 상태 변화는 어떻게 아나 | A의 조작이 B 구역을 열면 재방문·알림 정책에 따라 난이도가 달라짐 | 원본 원격 효과 유지. 숨은 변화 전체를 자동 통지하지 않고 저장 관측은 과거 스냅샷으로 취급 |
| 원본 자체가 잘못된 경우는 없나 | 분할 오류와 원본 오류를 구별해야 함 | 1-4는 원본 단서 순환으로 제외. 2-3 easy는 선반 진입 연결 누락이 있어 참조 행동 하나를 생략한 탈출 경로로 검사 |
| 문제별 협력 부담이 같은가 | 초반부터 정보가 필요한 문제와 마지막 암호만 교차하는 문제를 평균내면 의미가 흐려짐 | 핵심 6/확장 4/대조 1/제외 1. 연구실 2-4는 메시지 제거 시 막히는 참조 행동이 3/57로 후반 병목형 |
| 더 많은 난이도를 먼저 추가할까 | 현재 실패가 많은데 규모만 늘리면 원인을 찾기 어려움 | 현재 easy 12개 분할, 11개 평가. default/hard는 설명·피드백 외 일부 데이터 차이도 있어 별도 검증 필요 |

### 정보와 물건의 전달

| 고민 | 왜 중요했나 | 현재 상태와 남은 질문 |
|---|---|---|
| 무엇을 언제 요청·공유해야 하나 | 상대가 필요한 것을 모르는 상태에서 관련성을 판단해야 함 | 자유 텍스트 send. 요청·응답·자발적 공유를 로그에서 구별해 볼 필요 |
| 정보를 보내는 것과 물건을 주는 것이 같은가 | 코드 설명은 복사 가능하지만 도구는 소유권이 이동함 | send와 give 분리. Peer는 별도 가방, Solo는 공유 가방 |
| 없는 물건을 주거나 쓰려는 이유 | 발견·수집·소유·소모를 혼동할 수 있음 | 현재 가방을 매 판단 제공하고 엔진이 검증. 거울 Solo는 칼을 드러낸 뒤 수집하지 않고 사용하려 해 실패 |
| 물건을 발견하면 자동 수집되는가 | ‘보인다’와 ‘가방에 있다’를 모델이 구분해야 함 | 보이는 도구를 click해야 수집. 상태 설명에 이름이 있다고 바로 apply/give할 수 없음 |
| 해치까지 이동해야 하는가 | 전달 거리·왕복 이동이 협력 비용을 크게 바꿈 | 현재 give는 위치·거리 제한 없이 즉시 전달. 물리적 해치 장소는 구현하지 않음 |
| 대화량·전달 횟수를 비용으로 셀까 | 무료 대화와 유료 행동은 다른 과제임 | send/give 각각 1환경 행동. 메시지는 최대 300자, 초과 시 오류. 이 선택의 민감도는 미검증 |
| 전달되면 상대가 활용했나 | 전송 성공이 올바른 내용·이해·사용을 뜻하지 않음 | 수신 로그와 이후 행동을 연결해야 함. 같은 요청 반복이나 불완전 정보도 검토 |
| 메시지 속 명령이 실행되는 오류 | send 안의 apply 예시를 파서가 실제 행동으로 뽑으면 평가가 깨짐 | 명시적 Action 줄의 외부 명령만 처리하도록 수정. 메시지 본문 속 명령은 텍스트로 유지 |

### 관측과 프롬프트와 명령 실행

| 고민 | 왜 중요했나 | 현재 상태와 남은 질문 |
|---|---|---|
| 매 턴 전체 상태 JSON을 주는가 | 숨은 물건·정답·상대 정보를 노출할 위험 | 원본 엔진의 보이는 설명·대상·이동 라벨·가방을 텍스트로 제공. 평가용 JSON 전체는 입력하지 않음 |
| 전체 맵인가 현재 장면인가 | Solo가 어디까지 아는지에 따라 비교가 달라짐 | Solo도 A/B의 현재 두 위치와 실제 관측 기억만 제공. 미방문 전체 맵을 알지 못함 |
| 이름이 비슷한 명령을 받아줘야 하나 | 이동 라벨 불일치가 추론 실패처럼 집계됨 | 현재 정확한 대상·라벨을 요구. 예: move(dining table close-up)이 표시된 To the dining table close-up과 달라 거부됨 |
| Thought와 Action이 맞지 않는가 | 말로 설명한 계획이 실행으로 이어지지 않는 경우가 있음 | Thought는 공개된 짧은 설명만 관찰 가능. 내부 이해를 확정하지 않고 출력·실행 결과를 비교 |
| 출력 지시 자체가 충돌하지 않나 | Solo만 형식 때문에 손해를 볼 수 있음 | 공통 2줄 지시 제거. Solo Thought/Role/Action, Peer Thought/Action으로 수정 |
| 한 번에 여러 행동을 출력하면 | 순서·역할·비용이 모호해짐 | 현재 한 판단 한 행동. 여러 Action/Role은 무효. Phi Solo에서 이 문제가 계속 관찰됨 |
| 돌아다니지 말라는 지침이 탐색을 막나 | 상태가 바뀐 방에 돌아가야 하는 퍼즐이 있음 | 무조건적 반복·왕복 회피를 상태 변화 시 재방문·재시도 허용으로 수정 |
| 프롬프트가 너무 길어서 못하나 | 관측·규칙·기억이 행동 선택을 어렵게 할 수 있음 | 최신 실제 입력 최대 4,112토큰으로 8,192 문맥 초과는 아님. 길이·배치·주의 분산의 영향은 남음 |
| 자연어 명령을 구조화할까 | 협력보다 문자열 형식 준수를 측정할 수 있음 | 자유 텍스트 형식 유지 중. JSON/도구 호출/선택지 방식은 별도 조건으로 검증할 선택지 |
| 원본과 같은 실험인가 | 원본 성능과 직접 비교할 수 있는지 결정됨 | 원본 행동·관측을 기반으로 했지만 기억·Solo/Peer·도움·모델·정밀도·문맥이 달라 완전 재현은 아님 |

### 기억과 과거 경험

| 고민 | 왜 중요했나 | 현재 상태와 남은 질문 |
|---|---|---|
| 최근 10턴이면 충분한가 | 이동하면 예전 단서가 사라지고 같은 실패를 반복할 수 있음 | 최근 10행동/역할 외 관측·발견·수신·피드백 기록 추가 |
| 한 번만 나타나는 단서는 어떻게 보존하나 | 정상적으로 발견해도 이후 프롬프트에서 사라질 수 있음 | 2-2의 1040은 서랍 개방 결과에만 등장. 발견 기록 3,000자 범주를 추가해 보존 검사 |
| 현재 장면을 기억에 또 넣지 않나 | 중복이 중요한 과거 단서를 밀어냄 | 현재 장면은 저장 관측 표시에서 제외. 과거 행동 메뉴도 제외 |
| 실패 피드백이 기억을 다 차지하지 않나 | 오류 반복이 유용한 관측을 밀어내는 악순환 | 범주별 예산 분리. 오류는 최근 행동에 남기고 별도 저장 피드백에서는 제외 |
| Solo 기억이 Peer보다 작지 않나 | 중앙 기준선의 불공정한 불이익 | 과거 총 12,000자 정책 수정. 역할당 9,000자 동일 선택 정책, Solo는 양쪽 합산 최대 18,000자 |
| 기억은 실시간인가 | 예전의 잠긴 문 설명을 현재 사실로 오인할 수 있음 | 시점 있는 스냅샷. 상대 조작 이후 재관측·메시지 필요 |
| 메모리가 객관적 단서만 남기나 | 어떤 성공을 저장할지 환경이 골라주는 것도 설계 개입 | 현재 key step 증가에 따른 발견 저장은 외부 기억 정책. 자유로운 모델 메모나 전체 대화 이력과 동일하지 않음 |
| 새 채팅이면 아무 기억도 없어야 하나 | 실험 간 정보 누출 차단과 게임 내 기억 제거를 혼동할 수 있음 | 다음 절처럼 실행 간 격리와 실행 내 기록을 별도로 정해야 함 |

현재 저장 기억 한도는 역할당 관측 4,000자 + 발견 3,000자 + 수신 1,500자 + 피드백 500자다. 현재 관측·가방·최근 행동 등은 이 한도 밖에 추가되므로 9,000자가 전체 프롬프트 길이를 의미하지 않는다.

### Solo 기준선과 차례와 비용

| 고민 | 왜 중요했나 | 현재 상태와 남은 질문 |
|---|---|---|
| Solo가 원본 단일 플레이면 공정한가 | Peer만 두 시작점과 분할 지름길을 얻을 수 있음 | 같은 분할 환경에서 A/B를 한 에이전트가 제어하도록 수정 |
| Solo도 요청·전달해야 하나 | 자기 자신에게 메시지·물건을 주는 인위적 비용 | 요청·전달 제거, 공유 가방 하나. 수집·소모·조합을 양쪽에서 공유 |
| Solo의 정보가 더 많으면 항상 더 잘해야 하나 | 관측 이점과 탐색 선택 부담은 다름 | 우위는 가설. 실제로 Solo 역할 편중과 Peer 탐색 분산이 가능하므로 경로 분석 필요 |
| A/B를 매 턴 번갈아야 하나 | 한쪽이 막혀도 불필요하게 행동을 소비 | 현재 Peer는 연속 최대 4판단, 성공 send/give 또는 yield 시 상대에게 전환 |
| 막힌 A를 쉬게 하면 열쇠를 못 찾지 않나 | 국소적으로 막힌 것을 전체 탐색 불가로 오판 가능 | yield는 한 번의 양도, 영구 비활성화 없음. 실패만으로 할 일 없음 판정하지 않음 |
| wait/yield는 무료인가 | 무한 무료 추론이 생길 수 있음 | 유효 yield는 환경 비용 0이나 판단·모델 호출 소비. 500행동과 1,000판단을 별도 제한 |
| 동일 행동 수면 공정한가 | Peer 통신과 Solo 역할 선택이 예산에 다르게 작용 | 팀 환경 행동을 주 예산으로 사용. 모델 호출·토큰·비용도 함께 보고할 필요 |
| 스케줄러가 협력을 대신하지 않나 | 자동 교대가 탐색을 돕거나 흐름을 방해할 수 있음 | 연속 4판단은 현재 선택일 뿐 최적값 아님. 시작 역할·역할 배정·상한 민감도 남음 |

### 평가와 해석과 실험 운영

| 고민 | 왜 중요했나 | 현재 상태와 남은 질문 |
|---|---|---|
| 모두 탈출 실패면 무엇을 비교하나 | 성공률 바닥 효과로 H1 등을 검증하기 어려움 | 진행률·협력 병목 도달·오류 유형 병행. 성공률도 함께 유지 |
| Peer 진행률이 두 배 집계되는가 | 양쪽 수집으로 점수가 쉽게 늘 수 있음 | 전역 key step + 도구 수집으로 계산해 중복 합산은 아님. 쉬운 행동의 분산 탐색 효과는 남음 |

| 발견했는데 기억에서 빠지면 누구의 실패인가 | 전송 실패로 라벨링하면 기억 정책의 영향을 숨김 | 환경 노출, 현재 프롬프트 포함, 실제 전송, 후속 사용을 따로 추적해야 함 |
| 숫자가 메시지에 있으면 올바르게 전달한 건가 | 잘못된 대상·부정문·불완전 설명도 가능 | 정답 문자열 검사만으로 의미 판정 불가. 사람 검증 표본 필요 |
| 아직 도달하지 않은 단계도 실패인가 | 앞단 실패 때문에 전송·활용 기회 자체가 없을 수 있음 | 각 단계의 기회·선행 조건을 확인하고 도달하지 못함을 구별해야 함 |
| 50스텝 뒤 힌트를 주면 되나 | 힌트와 강제 행동이 협력·자율 해결을 대신함 | 현재 본 실험 무힌트. 도움 조건은 별도로 평가 |
| Oracle이면 원인을 분해할 수 있나 | 정답을 받은 LLM도 실수하고 정보를 과하게 줄 수 있음 | 주 실행 미구현. 스크립트/LLM 여부, 답변 범위·타이밍·비용을 먼저 정의해야 함 |
| 큰 모델이나 다른 모델이면 해결되나 | 능력·출력 형식·기억·설정을 동시에 바꾸면 원인 분리 불가 | 모델만 바꾸는 비교를 먼저 제안. 입력 형식이나 기억 변경은 별도 조건 |
| 실패 기록마다 프롬프트를 고쳐도 되나 | 특정 문제·모델에 맞춘 사후 최적화 가능 | 공통 원인을 확인하고 사전 고정한 소수 문제에서 검증. 변경 이력·버전 분리 |
| GPU 오류·12시간 제한은 어떻게 집계하나 | 계산 중단을 퍼즐 실패로 오인 가능 | OOM·중단은 결측. 모델 다운로드·스토리지·재개는 운영 문제이며 능력 판정과 구분 |

## 최신 결과가 실제로 보여준 것

- **형식 문제:** Phi Solo 5,500판단 중 602회가 여러 Role/Action 출력으로 무효였다. Solo 프롬프트의 과거 2줄/3줄 모순을 고친 뒤에도 발생했다.
- **반복 문제:** Qwen 거울 Solo는 같은 `craft(shard_1, shard_2)`를 총 418회 시도했다. 정상 종료 42개 중 34개는 마지막 200판단 이상 점수 증가가 없었다.
- **역할 선택 문제:** Qwen 거울 Solo는 A 488/B 12판단이었다. 양쪽 정보를 볼 수 있어도 양쪽을 충분히 탐색하지 않을 수 있다.
- **전달과 활용 문제:** 완료 Qwen Peer 10개에서 성공 메시지 886회, 물건 전달 8회였다. 요청 반복이 있어 전송 횟수를 협력 품질로 읽을 수 없다.
- **문맥 길이:** 실제 실행 최대 입력은 Qwen Solo 4,112, Peer 3,538토큰이었다. 문맥 상한 초과는 이번 정체를 설명하지 못하지만 입력 복잡성의 영향은 남는다.
- **인프라 결측:** Qwen 2-2 Solo와 3-2 Peer는 OOM. 0점으로 넣지 않고 보충할 대상으로 남긴다.

이 사례들은 “강한 모델에도 똑같이 발생한다”는 증거가 아니다. 다음 검증은 그런 구분을 위한 것이다.

## API 또는 새 채팅으로 무엇을 확인할까

### 메모리 없이의 의미부터 구분

| 의미 | 이번 목적과의 관계 |
|---|---|
| 이전 연구 대화·정답 설명·다른 에피소드 경험을 넣지 않기 | 평가에 필요한 격리 조건. 모델에 현재 허용된 정보만 전달 |
| 매 판단 독립 호출로 시작하되 시스템이 관측·기억을 다시 제공하기 | 현재 러너와 대응하는 방식. 호출 자체는 독립이어도 입력에 게임 기억은 존재 |
| 한 게임을 같은 채팅에서 계속하며 대화 이력을 누적하기 | 기존 최근 기록·외부 기억과 다른 조건. 추가로 남는 과거 정보 때문에 직접 비교 시 명시 필요 |
| 매 판단 현재 장면만 주고 과거 정보까지 없애기 | 별도의 무기억 조건. 방금 받은 암호·지난 실패도 잊게 하므로 주 평가 목적과 구분 |

**첫 비교에는 ‘이전 연구 문맥은 격리하고, 현재 러너가 만든 system/user와 게임 기억은 그대로 전달’하는 방식을 제안한다.** 현재 우리가 대화 중인 이 스레드는 정답·분할·실패 설명을 이미 포함하므로 평가용 새 실험 문맥으로 재사용하지 않는다.

Codex/Claude Code 같은 도구가 있는 실행 환경을 사용할 경우, 역할별 입력 외에 원본 YAML·정답 로그·상대 기록을 읽을 수 있는 작업공간을 함께 제공하면 관측 제한이 깨진다. 격리된 작업공간에 허용된 입력만 제공하거나, 환경 중계 인터페이스만 허용하는 방식이 필요하다. ‘새 채팅’이라는 이름만으로 격리가 검증되는 것은 아니다. 실제 세션 설정·도구 접근은 실행 전에 확인해야 한다.

### 환경은 프로그램이 유지하고 모델만 응답

```text
환경 엔진의 실제 상태
   ↓ 역할에 허용된 현재 관측 + 가방 + 선택된 기억
독립 모델 호출 또는 격리된 역할 채팅
   ↓ 원문 Thought / Role / Action
파서와 환경 엔진이 실제 행동 처리
   ↓ 성공 또는 오류 피드백 + 갱신된 실제 상태
다음 판단 입력 생성
```

모델에게 전체 YAML을 주고 게임 진행과 상태 판정까지 맡기면 숨은 상태가 드러나고 환경이 달라질 수 있다. 엔진은 현재 상태·소유권·잠금·비용을 판정하고, 모델은 주어진 관측에서 행동을 선택하게 한다.

수동 전달로 먼저 확인할 때에도 **명령은 원문 그대로** 엔진에 넣고 피드백을 반환한다. 사람이 잘못된 이름을 고쳐주거나 “다른 방을 봐라”라고 조언하면 그 턴부터 도움 개입으로 기록해야 한다. Peer는 A/B 입력을 분리하고 send/give로 허용된 정보만 중계한다.

### 확인할 실험을 순서대로 구분

| 검증 | 실행 방법 제안 | 답할 수 있는 질문 |
|---|---|---|
| 한 판단 진단 | 기존 실패 직전 system/user를 새 모델에 제공하고 한 행동을 받음 | 없는 물건·명령 형식·재탐색 선택을 개선하는가? 전체 게임 해결 증거는 아님 |
| 초기 상태부터 Solo | 동일 분할·관측·공유 가방·기억·무힌트 조건으로 진행 | 강한 단일 제어자가 실제 단서를 따라 진행할 수 있는가? |
| 같은 문제의 Peer | 독립 A/B 입력, 현재 전달·스케줄·팀 예산 유지 | 두 역할이 필요한 단서·도구를 발견·요청·전달·사용하는가? |
| 원인별 추가 비교 | 형식·기억·스케줄 중 하나만 별도 변경 | 그 요인이 성능 차이에 얼마나 기여하는가? |

대표 후보는 거울 1-1(양방향 연쇄), 아파트 2-1(기본 교환), 당구장 1-3(교환 부담이 낮은 대조)이다. 상점 2-2는 단서 보존·양쪽 정보 결합을 추가 검증할 때 유용하다. 결과가 나온 뒤 잘된 문제만 선택하지 않도록 실행 목록을 먼저 정한다.

첫 소규모 진단은 예를 들어 문제당 50환경 행동까지 정하고, 새 장소 탐색·유효 행동·실제 교환 여부를 확인할 수 있다. 이는 기존 @50과 비교할 진단이며 탈출 가능성의 판정 예산은 아니다. 협력 병목 도달 여부를 함께 기록한다. 전체 경로 실험의 행동 예산·호출/금액 상한과 중단 조건은 따로 고정한다.

새 모델의 이름·버전, 생성 설정, 추론 관련 설정, 출력 한도, 제공한 메시지, 원문 응답, 처리한 명령, 피드백, 토큰·비용을 저장한다. 기존 256출력토큰 조건을 그대로 쓸지 충분한 추론을 허용할지도 구분한다. 모델과 추론 예산을 함께 바꾸면 ‘기존 설정에서 모델만 교체한 비교’가 아니라 ‘더 강한 실행 조건에서의 가능성 검사’다.
