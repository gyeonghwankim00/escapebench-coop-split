# 현재 실행: 유연한 스케줄과 관측 기억 (프로토콜 v6 / nightly-v5)

Solo는 매 판단에서 `Role: A` 또는 `Role: B`와 `Action:`을 한 번의 모델 호출로
선택합니다. 두 위치는 유지하며, 선택한 쪽의 현재 장면에서 행동합니다. 양쪽 현재 관측과
공용 가방을 제공하고 send/give/yield는 허용하지 않습니다.

Peer는 한쪽이 최대 4판단을 연속 실행합니다. `yield()` 또는 성공한 send/give는 즉시
상대에게 넘기고, 상대도 같은 규칙을 따릅니다. 양도는 일시적이며 자동 휴면·종료가 없습니다.
오류도 연속 판단 수에 포함해 상대에게 기회가 돌아가도록 합니다. 이 상한은 정답·숨은 상태에
의존하지 않습니다. 메시지와 물건은 기존과 같이 거리 제한 없이 전달합니다.

- 기본 예산: 팀 환경 행동 500, 팀 판단 최대 1000. 각 호출의 토큰·생성 시간도 기록합니다.
- 유효한 yield는 환경 비용 0, 판단 비용 1. 다른 행동·잘못된 명령은 환경 비용 1입니다.
- Solo 역할 선택에는 추가 호출·환경 비용이 없습니다. 자유 선택의 이점도 기준선에 포함됩니다.
- 기본 도움 정책은 `none`: 정체해도 자동 정답·강제 행동·순간이동이 없습니다.
  `--help-policy original`을 명시하면 50환경 행동 정체 도움 및 10도움 판단 후 강제를 사용합니다.
  이는 분할 환경에 맞춘 도움이며 원본 실험과 완전히 동일한 프로토콜이라는 뜻은 아닙니다.
- 기억: 실제 관측한 장면의 마지막 설명·행동 목록, 받은 메시지와 행동별 마지막 피드백을 지속 저장합니다.
  프롬프트에는 최근 기록부터 총 12000문자 안에 완전한 항목만 넣고 누락 개수를 표시합니다.
  최근 행동은 역할별 10개, 도움 중에도 유지합니다. Solo는 양쪽 기억을 한도 안에서 통합합니다.
  로그의 observed_memory/received_memory가 전체 저장본이며 실제 모델 노출은 generation.messages입니다.
- 저장 관측은 마지막 관측 시점의 스냅샷입니다. 상대가 문을 열어도 숨은 전역 상태를 자동
  공개하지 않습니다. 변경 후 재방문·이전 실패 재시도가 유효하다는 지침을 두 조건에 제공합니다.
- 엄격한 Action: 한 줄만 실행합니다. send 안의 괄호·행동 예시는 문자열로 전달합니다.
  300자 초과 메시지는 오류로 반환하고 일부만 전달하지 않습니다.

결과에는 environment_actions/action_cost/decision, 역할별 행동 수·방문 장소 수,
메시지·전달·양도·오류·입출력 토큰, 힌트·강제 행동을 기록합니다. 고정 예산 집계는
판단 줄 수가 아닌 환경 행동 누적으로 자릅니다. 중단·판단 예산 소진으로 부족한 예산 관측은
0점 처리하지 않습니다. 탈출은 원본 종료 조건이고, 진행률 100%와 별개입니다.

분할 검사 `python -m scripts.audit_split_paths --output data/split_audit_v6.json`은
정답을 알고 도달 가능한 곳으로 무료 이동하는 보수적 선별 검사입니다. game1-1, game1-3,
game2-4, game3-1은 control_or_review로 분리합니다. 암호를 미리 아는 가정 때문에 정보 의존성
생략을 실제 우회로 오인할 수 있으므로, 당구장 이외 문제는 비용 있는 경로와 단서 검토가 필요합니다.
나머지 8문제도 main_candidate이며 완전히 검증됐다는 뜻은 아닙니다. 집계의 주 평균은 동일
문제·동일 예산에서 관측이 완성된 main_candidate 쌍만 사용합니다. 모든 12문제는 진단용으로
실행하며 원본 데이터를 임의 수정하지 않습니다. 검사 입력은 결과 폴더에 동결합니다.

프로토콜 `escapebench-adaptive-v6`, 새 폴더 `nightly-v5`를 사용합니다. 구 결과와 이어 돌릴 수
없으며 모델 파일은 재사용합니다. 아직 서버에 제출하지 않았습니다.

로컬 업로드: `bash server/upload.sh`.
서버 프로젝트에서 제출: `bash server/submit-nightly.sh`.
결과 다운로드 시 기존 안내의 폴더명을 `nightly-v5`로 사용합니다.

# 현재 Solo: 정보·가방 통합 (프로토콜 v5 / nightly-v4)

Solo는 **분할된 A/B 환경을 한 컨트롤러가 관측하고, 실제 공용 가방 하나로 푸는 조건**입니다.
원본 EscapeBench의 단일 시작 위치로 돌아가는 조건은 `original_solo`입니다.

| 규칙 | Solo | Peer (`coop`) |
|---|---|---|
| 장면 분할·장치·A/B 시작 위치 | 동일 | 동일 |
| 이번 턴의 관측 | A/B의 현재 장면을 함께 제공 | 행동하는 역할의 현재 장면만 제공 |
| 기억 | A 최근 10행동 + B 최근 10행동·피드백 | 자기 최근 10행동·피드백과 수신 내용 |
| 가방 | 실제 공용 가방 하나, 프롬프트에 한 번 표시 | 역할별 가방 |
| 수집 후 다른 쪽에서 사용 | 즉시 사용 가능, 전달 턴 없음 | give로 전달해야 사용 가능 |
| 메시지·전달 | send/give 불가 | send/give 각각 팀 1행동 |
| 위치·행동 | A/B 교대, 활성 위치에서 한 행동 | 동일 |
| 기본 행동 | click/apply/input/craft/move | 동일 + send/give |
| 예산·생성 | 팀 500행동, 기존 greedy 설정, 문맥 8192 | 동일 |

수집·사용·조합·이동·잘못된 행동은 각각 한 행동을 소비합니다. 양쪽 관측을 읽거나
공용 가방을 접근하는 데 별도 행동은 없습니다. A에서 수집한 열쇠는 B의 다음 차례에
즉시 사용할 수 있으며, 사용 후 소모되면 양쪽에서 동시에 사라집니다. 실제 하나의 Bag을
공유하므로 복제·중복 수집 점수는 없습니다. `send`/`give`를 출력하면 명시적인 오류와
한 턴 소비로 처리하며, 무료 재생성이나 다른 행동으로 자동 변환하지 않습니다.

정보 통합은 현재 관측과 동일한 기억 창의 통합을 뜻합니다. 숨은 물건·미탐색 장면·
정답은 공개하지 않고, 기존에 방문한 모든 장면을 자동으로 다시 관측하지도 않습니다.
A/B 위치는 따로 유지합니다. 이번에 B의 장면을 읽었다고 A 차례에 B에서 행동할 수는
없습니다. 자유로운 역할 선택까지 도입하면 스케줄 효과도 바뀌므로 이번 비교에서는
교대를 고정합니다. 원본 장치의 원격 효과와 접근 규칙은 두 조건에 똑같이 적용합니다.

50행동 정체 시 도움 및 도움 중 10회 뒤 강제 행동 정책은 유지합니다. Solo의 도움은
원본 정답 행동을 대상 장면의 역할에 직접 주고, 전달 힌트는 만들지 않습니다.
이 도움에는 위치 이동·정답 공개가 포함되므로 도움 이후 진행률을 자율 해결 능력으로
해석하면 안 됩니다. 정답 도움으로 12문제 모두 완료되는 검증은 환경의 풀이 가능성 검증입니다.

해석할 비교는 **중앙 통제와 무료 정보·물건 공유 대 분산 통제와 유료 통신·전달**입니다.
점수 차이를 순수 추론 능력 차이나 통신 실패만으로 설명할 수 없습니다. 동일 팀 행동
예산의 진행률, 첫 도움 전 진행률·행동 수, 힌트/강제 행동 수, 메시지·전달 비용,
오류율과 모델 토큰 사용량을 함께 봅니다. 첫 도움 전 길이가 다른 비교도 주의합니다.
Solo는 유리한 기준선이지만 더 큰 입력 때문에 실제 모델 점수의 수학적 상한은 아닙니다.
Solo 링크에는 협업 전송/전달 실패 단계를 부여하지 않습니다.

로그의 `shared_bag`가 Solo의 정식 재고이고 `inventory_mode=shared`를 기록합니다.
호환 필드 `bags.A/B`는 같은 재고의 접근 뷰이므로 합산하지 않습니다. 진행률은 원본
전역 체크포인트 카운터 하나로 계산합니다. 기존 v1~v4 프로토콜 결과를 새 결과와 합치거나
도중부터 이어 돌리지 않습니다. 새 출력은 `nightly-v4`, 프로토콜은
`escapebench-split-solo-vs-peer-v5`입니다. 모델 파일은 재사용합니다.

로컬에서 `bash server/upload.sh`로 올린 뒤 서버 프로젝트에서
`bash server/submit-nightly.sh`로 제출합니다. 이 수정 자체는 서버 작업을 제출하지 않습니다.

이하 내용은 과거 프로토콜과 실행 도구의 기록입니다. Solo 규칙과 출력 경로는 위 정의가 우선합니다.

# Solo 요청 제거 (프로토콜 v4 / nightly-v3)

Solo는 A/B 양쪽의 현재 관찰과 기록을 한 컨트롤러가 받습니다.
시스템 프롬프트는 원본 기본 행동 설명에 중앙 통제 규칙만 추가합니다.
Peer의 “상대 장면·가방을 볼 수 없다”는 문구는 포함하지 않습니다.

- 텍스트 요청/통신 `send`는 Solo에서 금지합니다. 엔진도 거부하며, 모델이 출력하면
  그 턴을 소비하는 오류로 기록합니다. 자동 교정이나 무료 재질문은 하지 않습니다.
- 물건 전달 `give`는 허용합니다. 가방을 역할별로 유지하므로 도구를 상대 가방으로
  옮기는 물리적 행동은 여전히 필요하며, Peer와 같은 한 팀 행동을 소비합니다.
- Solo는 A에게 다음 행동을 “요청”할 필요가 없습니다. A 차례가 오면 같은 컨트롤러가 직접
  수집/전달을 결정합니다. 이번 차례에는 현재 역할의 유효한 행동 하나만 실행합니다.
- Peer의 send/give, A/B 스케줄·시작 위치·가방·기억·예산은 기존 규칙을 유지합니다.

전체 파이프라인의 새 출력 폴더는 `nightly-v3`입니다. 기존 `nightly-v2`는 저장된 그대로 보존합니다.
모델 파일을 재다운로드할 필요는 없으며, 현재 명령으로 제출하면 새 프로토콜의 점검과 실행을 수행합니다.
아래 v2 안내는 당시 구현 기록입니다. 새 결과를 받을 때는 경로의 nightly-v2를 nightly-v3로 바꿉니다.

# Solo 조건 수정: 같은 A/B 환경의 중앙 통제 (protocol v3)

현재 `solo`는 **분할된 A/B 환경에서 한 에이전트가 양쪽 현재 관찰을 받는 조건**이다.
`coop`는 같은 환경의 A/B 역할이 자기 관찰·기록만 받고 send/give로 협력하는 조건이다.

| 항목 | Solo | Peer (`coop`) |
|---|---|---|
| 분할·A/B 초기 위치·장치 상태 | 동일 | 동일 |
| 가방·이동·물건 전달 규칙 | 역할별 분리, give 필요 | 역할별 분리, give 필요 |
| 스케줄·예산 | A/B 교대, 팀 500행동 | A/B 교대, 팀 500행동 |
| 관찰 | 양쪽의 현재 관찰 | 행동 역할의 현재 관찰 |
| 기억 | A 최근 10행동 + B 최근 10행동 | 각자 최근 10행동과 수신 업데이트 |
| 행동 | 이번 활성 역할의 한 행동 | 이번 활성 역할의 한 행동 |
| 프롬프트 문맥 상한 | 8192, 초과 시 오류 | 8192, 초과 시 오류 |

Solo의 전체 관찰은 실제 현재 장면에 보이는 것과 각 가방에 한정한다.
미탐색 장면, 숨은 물건, 정답·평가 주석은 공개하지 않는다.
중앙 관찰을 만드는 동안 장치 상태·진행 카운터·행동 캐시·우편함을 변경하지 않는다.
Solo는 상대에게 정보를 요청할 필요 없이 같은 정보를 직접 보지만, send도 같은 비용으로 사용할 수 있다.
원본 50행동 정체 도움과 강제 행동은 같은 분할 엔진의 역할별 도움 규칙을 사용한다.

기존 원본 단일 플레이는 `original_solo`로 실행할 수 있다.
구 프로토콜의 `solo` 파일은 **그대로 보관**하며 새 Solo로 재분류하지 않는다.
`matrix_report`는 구 Solo를 original_solo로 표시하여 새 Solo/Peer 쌍에서 제외한다.
`nightly-v1`은 과거 실험이고, 이번 수정은 `nightly-v2`에 저장한다.
Phi 준비 점검도 v2에서 다시 통과해야 한다. 다운로드한 모델 파일은 재사용한다.
실행 중인 v1 작업은 수정된 코드로 재개하지 말고 별도 결과로 보존한다.

# 현재 단계: 다른 계열을 포함한 500행동 파일럿

전체 모델 순위를 내기 전에 Qwen에서 보인 경향이 다른 계열에서도 나타나는지 점검한다.

원본의 50행동 정체 도움 규칙을 유지한다. 진행률은 고정된 50/200/500행동 시점에서

모델 간 동일 게임의 Solo/Peer 변화를 비교하고, 도움 전 실제 요청·전달·활용과 접근성 문제를 함께 본다.
모델 성적과 별개로 정답 재생·정보/물건 접근성 검증이 필요하다. 이 파일럿만으로 데이터셋 타당성을 확정하지 않는다.

점검 성적에 따라 문제나 프롬프트를 바꾸지 않으며 해당 데이터는 본 파일럿 집계에서 제외한다.
실제 제출·재개·다운로드는 [server/README.md](../../../server/README.md)를 따른다.

# 고정 코호트 v1: 전체 easy 문제에서 모델 크기와 Solo/Peer 비교

## 현재 주 실험

상태 진단 4개는 오류 가능성을 찾는 탐색 분석으로 종료한다. 그 사례를 기준으로 프롬프트,
분할, 정답, 문제 표본을 조정하지 않는다. 아래 조건을 고정한 뒤 전체 결과에서 경향을 확인한다.

- 표본: 원본 easy 12문제 전부. 각 문제에서 Qwen3-14B/32B × Solo/Peer, 총 48회.
- 생성: NF4 4비트, batch 1, greedy, 출력 256토큰, 문맥 상한 4096, native thinking 끔.
- 입력: `interface=original`. upstream 짧은 `Thought:`/`Action:` 형식과 최근 10행동 기억 유지.
  Thought는 모델이 출력한 설명이며, 내부 사고의 직접 관측값이 아니다.
- Peer: 기존 v3 분할, 별도 가방/기억, A/B 교대, send/give 유지. 분할/시작 위치를 재선정하지 않는다.
- 예산: 최대 4000 팀 행동. Peer에서 A/B 각각 4000이 아니며 메시지/전달도 행동 예산을 사용한다.
- 원본의 50행동 정체 도움과 도움 후 강제 행동 규칙을 유지한다. 매 턴 추가하는 형식 안내와 다르다.
- 원본 데이터는 수정하지 않는다. game1-3 여행가방의 설명 상태 전이 누락은 원본의 알려진 한계로 기록한다.
- 이미 수행한 batch 2/4 파일럿과 상태 진단은 주 실험의 결측값을 대체하지 않는다.
- 동일 greedy 반복을 독립 표본으로 세지 않는다. 첫 코호트는 각 조건 1회이며 추론 단위는 게임 12개다.

## 분석 기준

주 비교는 게임별 Solo/Peer 차이와 그 차이가 모델 크기에 따라 어떻게 바뀌는지다.
50/200/500/1000 팀 행동의 진행률을 기록하되, **그 시점의 도움 수와 강제 행동 수도 함께** 보고한다.
도움을 받은 고정 예산 성능을 자율 성능으로 부르지 않는다. 먼저 탈출한 경우 이후 예산에는
탈출 진행률과 당시 도움 수를 유지한다. 중단/오류로 해당 예산에 미달한 경우는 결측이다.

최초 도움 전 진행률에는 최초 도움 시점도 붙인다. 각 조건의 자율 구간 길이가 다르므로
그 수치만으로 협업 향상이나 모델 우월성을 주장하지 않는다. 성공률, 총 행동 수, 총 도움 수,
강제 행동 수, 무효 명령, 출력 제한, 모델 호출/토큰 수를 함께 본다. 도움 이후 성공과 무도움 성공은 구분한다.
`run_matrix`와 `analyze_collaboration`의 기존 전체/도움 전 집계를 그대로 활용한다.
코드 단서/물건 전달 링크는 한 게임 안에 종속되어 있으므로 독립 표본 수로 더하지 않는다.
실패 사례는 전체 결과에서 정한 분류별 빈도를 설명하는 예시로만 쓴다.

Solo/Peer 차이에는 분할로 인한 관찰량 감소, 시작 위치, 분산 탐색, 두 개의 기억 창,
메시지 비용이 함께 포함된다. 이 비교만으로 순수한 대화의 인과 효과를 분리하지 못한다.
전체에서 반복되는 차이가 확인된 뒤 별도 버전으로 communication-off 등의 절제 실험을 설계한다.
성능이 좋은 문제만 남기거나 기존 결과를 보고 주 실험 프롬프트를 덮어쓰지 않는다.

## 현재 실행 순서 (generation 2)

1. 로컬 `bash server/upload.sh`로 올립니다.
2. 서버 `~/escape-lab`에서 `bash server/submit-pilot.sh`를 실행합니다.
3. 14B 점검 작업(각 70행동)이 통과하면 거울·실험실 Solo/Peer 4에피소드와
   낮은 상호의존 당구장 Solo/Peer 2에피소드가 각각 GPU 1장에서 배치로 실행됩니다.
4. 파일럿의 도움 전 진행·교환과 환경 오류를 확인한 후 12문제/8B로 확장합니다.

기존 다운로드 결과는 v1 분할 및 generation 1입니다. 로그에서 `do_sample=True`로 모델 기본값이
병합된 경고가 확인되어, Solo도 새 greedy 기준선으로 재사용하지 않습니다.
`greedy_generation.py`는 `use_model_defaults=False`와 명시적 생성 인자를 함께 전달하며,
실제 `generate()`의 설정 준비 단계에서 `greedy_search` 및 고정 인자를 검사합니다.
검사를 거치지 않거나 값이 달라지면 중단합니다. 확정 설정은 매 생성의 `effective_generation`에 저장됩니다.
`temperature=1.0`, `top_p=1.0`, `top_k=50`은 중립값이며 **샘플링을 하지 않으므로 적용되지 않습니다**.
원본 temperature=0 동작은 `do_sample=False`의 greedy로 구현합니다.

### 단서별 분석

협업 실행이 종료/중단될 때 `coop/<game>/collaboration.json`과 `collaboration.md`를 생성합니다.
원본 프롬프트/행동을 바꾸지 않으며, 로그에만 `evaluation`(행동 전 가방, 현재 장면, 이동 가능한 자기 장면)을
추가합니다. `evaluation_inputs/`의 분할·단서 주석은 실행 당시 파일 그대로 고정하며 모델에게 보여주지 않습니다.

- `before_first_hint`: 첫 실제 도움 턴 직전까지의 자율 구간. 도움 이후 일반 모드도 이 구간에 넣지 않습니다.
- `full_episode`: 도움/강제 행동을 포함한 전체 기록. 자율 성능으로 해석하지 않습니다.
- 코드 단서: 원래 보유 역할의 관찰/가방/다시 제시된 환경 피드백에서 주석 근거가 나타났는지,
  상대가 실제 받은 업데이트에 정답 또는 근거 문구가 있는지, 정답 입력이 성공했는지를 추적합니다.

## 두 조건에서 같은 것 / 다른 것

| 항목 | Solo | 2-agent |
|---|---|---|
| 엔진·YAML·진행률 | 원본 | 동일 (세계 상태 하나 공유) |
| 시스템 프롬프트 | 원본 `BASE_SYS_PROMPT_COT` | 원본 + 협업 문단 1개 (reminders 앞에 삽입) |
| 관찰·기록 형식 | 원본 `describe()`, 최근 10스텝 | 동일, 역할별 자기 기록만 |
| 생성 | greedy, 256토큰, thinking 끔 | 동일 |
| 문맥 상한 | 4,096토큰 | 동일 |
| 행동 예산 | 4,000 | 팀 합계 4,000 (A→B→A… 교대) |
| 정체 판정 | 50스텝 무진행 | 팀 진행 기준 50스텝 |
| 추가 행동 | 없음 | `send(message)`, `give(tool)` |
| 이동 | 원본 인접 이동 | 자기 장면만. 상대 장면을 지나는 연결은 `Go to X via partner area`로 표시 |

**동등성 보장:** 모든 장면을 A에 주고 협업 기능을 끈 `CoopAgent`는 원본 에이전트와
프롬프트·로그·강제 행동이 스텝 단위로 같다(`test_all_scenes_to_one_role_reproduces_original_agent`).
따라서 협업 조건의 차이는 위 표의 추가 규칙에서만 생긴다.

## 협업 규칙 세부

- **장면 소유:** 각 원본 장면은 A 또는 B 하나에 속한다. 자기 장면의 물건만 보고 조작한다.
- **이동:** 상대 장면은 들어갈 수 없지만 지나갈 수는 있다. 지나는 상대 장면과 목적지가 모두
  원본에서 visible이어야 한다. 잠긴 문 뒤는 원본처럼 막힌다.
- **시작 (두 방 시작):** A는 원본 시작 장면에서 시작한다(Solo와 같은 첫 화면). B는 역할 파일의
  `starts.B` 장면, 즉 자기 방 안에서 시작한다. 원본에서 그 방이 잠겨 있어도 B는 이미 안에 있다.
  B 방 내부의 잠금은 원본대로 남는다. 시작 장면이 엔진에서 아직 숨김이어도 B는 자기 차례에 그 장면으로
  돌아갈 수 있다(안에 있으므로). 상대는 문이 열릴 때까지 그 장면을 지나갈 수 없다.
- **시작 (v1 규칙, `starts` 없을 때):** 상대 역할은 원본 시작점에서 visible 경로로 자기 장면에 닿을 때
  처음 닿는 장면에 들어오고, 그 전에는 모델 호출 없이 차례를 건너뛴다.
- **가방:** 역할마다 따로. 원본 엔진의 전역 가방을 매 차례 해당 역할 것으로 바꿔 끼운다.
  조합(craft)은 두 도구가 같은 가방에 있어야 한다.
- **메시지:** `send(...)`는 다음 상대 차례 프롬프트의 `Updates from your partner since your last
  action:`에 표시된다. 이후에는 받은 사람의 기록 항목(최근 10스텝 창)에만 남는다. 별도 메모장은 없다.
- **물건 전달:** `give(tool)`은 도구 객체(현재 상태 포함)를 상대 가방으로 옮긴다. 어디서나 가능.
- **상대가 일으킨 변화:** 원본 트리거(문 열림 등)는 상대 장면에도 그대로 적용되고, 알림 없이
  다음 관찰에서 보인다.

### 기준 (`scripts/search_splits.py`)

**나누는 단위.** 막다른 장면 묶음이 방이 아니라 "들여다보기"면 그것이 열리는 장면에 붙인다. 입구 장면 이름이
`... close-up`이거나, 처음부터 자유롭게 들어갈 수 있는 단일 장면인 경우다. 여러 장면으로 된 방과 잠긴 문 뒤의
단일 방은 독립 단위로 남는다. 따라서 어떤 역할도 상대 방 안의 확대 화면만 따로 갖지 않는다.

**필수 조건.**
1. give를 쓰면 원본만큼 풀 수 있다.
2. 두 역할 모두 상대가 아무것도 안 해도 정답 단계의 10% 이상을 혼자 끝낼 수 있다(노는 역할 없음).
3. 정답 단계의 15% 이상이 물건 전달 없이는 끝나지 않는다(협업이 실제로 필요). 어떤 분할도 이를 만족하지 못하는
   게임은 이 조건만 풀고 `low_interdependence`로 표시한다(game1-3 하나).

**선호 순서.** 방을 넘는 암호 단서가 하나라도 있는 분할 우선, 그다음 점수:
두 역할의 독립 진행량 최솟값(높게) − B 작업 비율의 50% 이탈(낮게) − 영역이 여러 덩어리인 정도(낮게)
+ 물건 전달 수(8까지) + 방 넘는 단서 수(3까지) − 전달 과다(12 초과).

12게임 모두 이 순서의 1위다. `python -m scripts.make_roles --verify`가 탐색을 다시 돌려 확인한다(약 2분).

## 도움(힌트) 정책

원본과 같다: 팀 진행률이 50스텝 동안 그대로면 남은 정답 로그의 첫 행동을 힌트로 주고,
목표 장면으로 이동시키고, 기록을 생략하고, 같은 목표에서 10스텝째에는 정답 행동을 강제 실행한다.
협업에서는 다음이 추가된다.

- 힌트는 목표 장면 주인에게 간다. 힌트 중에는 교대를 멈추고 그 역할만 행동한다.
- 필요한 도구가 상대 가방에 있으면 먼저 상대에게 `give(tool)` 힌트를 준다(10스텝째 강제).
  전달 후 실제 행동 힌트는 카운터를 새로 시작한다.

강제 행동으로 얻은 진행·탈출은 독립 해결이 아니다. `forced_action=true`, `generation=null`로 기록된다.

게임·조건·모델을 골라 낼 수 있다. 결과 폴더 이름에 게임 목록이 들어가므로(`outputs/matrix/8B-coop_2-3_3-1_…/`)
같은 구성은 이어서 돌고 다른 구성과 겹치지 않는다.

```bash
GAMES="game2-3-easy game3-1-easy game1-4-easy game1-5-easy" bash server/submit-matrix.sh   # 이 4게임만
CONDITIONS=coop MODELS=8B bash server/submit-matrix.sh                                      # 8B 협업만
PER_JOB_8B=4 PER_JOB_14B=2 bash server/submit-matrix.sh                                     # 작업당 게임 수(기본값)
```

- 8B는 작업당 4게임: smoke에서 잰 4개 동시 배치 ≈ 7.5초/회 → 4,000스텝에서도 약 8.5시간.
- 14B는 작업당 2게임: 이전 v1 실험에서 4에피소드 배치는 약 2.4~5.9시간이었다. 전체 확장은 긴 새 문제를 고려해 보수적으로 묶는다.
- 한 작업 안의 게임들은 GPU 배치를 공유한다. 작업 시간 ≈ 가장 긴 게임의 스텝 수 × 배치 1회 시간.
- 한 작업에 여러 GPU를 받는 방식은 쓰지 않는다. 한 노드에 빈 GPU가 동시에 여러 장 있어야 시작되기 때문이다.

동시에 몇 개가 도는지는 계정 한도에 달려 있고, 넘는 작업은 대기열에서 기다린다.

```bash
sacctmgr -p show assoc user=$USER format=User,Account,Partition,QOS,GrpTRES,MaxTRES,MaxJobs,MaxSubmit
squeue -u $USER -o "%.10i %.20j %.8T %.10M %R"   # Resources/Priority=빈자리 대기, QOSMax…/AssocGrp…=개인 한도
```

#### 분할이나 코드를 바꾼 뒤 (기존 작업을 멈춰야 하나)

- **분할만 바꾸는 경우 Solo 작업은 멈추지 않는다.** Solo는 분할과 무관하다. 생성 버전이 바뀌면 Solo도 별도 실행해야 한다. 코드 업로드 뒤에도 Solo 전용 작업은 이어서 돈다
  (재개 조건이 Solo가 쓰는 파일·설정만 본다). 같은 생성 버전의 이전 Solo 결과만 집계에 쓰인다.
- **아직 시작 안 한 협업 작업은 그대로 둬도 된다.** 시작할 때 새 코드와 새 분할을 읽는다. 대기 순서를 잃지 않는다.
- **옛 분할로 이미 돌고 있거나 끝난 협업 작업**은 결과가 `stale`로 분류되어 집계에서 빠진다. 돌고 있으면
  `scancel`하고, 그 폴더는 이름을 바꿔 보관한 뒤(재개가 거부되므로) 같은 게임을 다시 제출한다.

### 4. 모니터링

```bash
squeue -u "$USER"
tail -f matrix-smoke-<JOBID>.out          # [batch N] size=… s/batch 줄이 처리량
tail -f matrix-<JOBID>.out                # 게임별 100스텝마다 진행률·힌트 수
cat outputs/matrix/8B-coop/report.md
```

smoke가 끝나면 `outputs/matrix/smoke-8B-<JOBID>/timing.jsonl`의 `batch_seconds / batches`로
배치 1회 시간을 확인한다. 8게임 한 벌의 예상 시간 ≈ 배치 시간 × 게임당 최대 스텝(~3,000~4,000).
이 값이 11시간을 넘으면 자동 재제출로 이어지며 그대로 두면 된다.

### 5. 12시간 제한과 재개

- 러너는 시작 후 11시간 10분(또는 Slurm의 종료 5분 전 USR1)에 새 생성을 멈추고 완료된 스텝까지
  저장한 뒤 종료 코드 75로 끝난다. 생성 중이던 응답은 버리며 행동으로 적용하지 않는다.
- `matrix.sbatch`는 75를 받으면 **같은 인자로 자기 자신을 재제출**한다(기본 최대 4개 작업,
  `ESCAPE_MAX_ATTEMPTS`로 변경).
- 재개 시 완료된 에피소드는 건너뛰고, 미완료 에피소드는 저장된 응답을 모델 호출 없이 원본 엔진에
  재생하며 매 스텝 프롬프트·상태가 저장본과 같은지 확인한 뒤 이어서 추론한다.
- 기본 출력 디렉터리는 `outputs/matrix/g2-<크기>-<조건>`이며, 제출 래퍼는 게임 목록이나 파일럿 태그를 붙인다. 같은 출력 경로와 설정으로 다시 제출하면 재개된다.
- 코드·역할 데이터·모델·설정이 바뀌면 재개를 거부한다(Solo 전용 작업은 Solo가 쓰는 파일·설정이 같으면 재개). 새로 시작하려면 기존 디렉터리를 옮기거나
  `ESCAPE_OUT=outputs/matrix/새이름 sbatch server/matrix.sbatch …`.
- 오류(`error`)로 끝난 에피소드는 자동 재시도하지 않는다. 원인 확인 후 `--retry-errors`를 붙여 제출.

## 시간 예산 근거와 가정

- 기존 8B 실행 두 건에서 역산한 처리량: 입력 처리 약 3,500토큰/초, 생성 약 21토큰/초(배치 1).
- 순차 실행이면 8문제 한 벌에 8B 예상 약 15시간, 14B 약 26시간이라 12시간 안에 안 끝난다.
- 8게임을 한 배치로 생성하면 생성 단계의 GPU 시간을 공유해 8B 약 5.5시간, 14B 약 10시간으로
  추정한다. **배치 이득과 14B 속도는 측정값이 아니다.** smoke 결과로 확인한다.
- 넘치면 자동 재제출되므로 결과는 같고 벽시계 시간만 늘어난다.

## 원본 논문과 다른 점 (두 조건 공통)

- HF Transformers/SDPA + NF4 4비트, GPU 1장 (원본 공개 예시는 vLLM/BF16).
- 문맥 상한 2,400 → 4,096. Solo 프롬프트도 최대 약 8,400자라 2,400토큰을 넘을 수 있다.
  잘라내지 않으며, 넘치지 않는 스텝의 결과는 달라지지 않는다.
- 배치 greedy 생성(left padding). 배치 크기 1과 드물게 다른 토큰이 나올 수 있다.
  필요하면 `--max-batch 1`로 순차 생성할 수 있지만 12시간 안에 끝나지 않는다.
- Qwen3 native thinking 끔. 원본의 짧은 Thought/Action 지시는 유지.

## 남는 한계

- 분할 지표는 원본 정답 로그를 행동 어휘로 쓴 탐욕적 근사다. 실제 모델이 그만큼 혼자 할 수 있다는 뜻이 아니다.
  분할을 바꾸면 `scripts/make_roles.py` 수정 후 재생성한다. 이전 분할의 협업 결과는 집계에서 자동 제외된다(stale).
- 협업 힌트는 원본에 없는 확장이다(전달 힌트). 힌트 수 비교 시 give 힌트 수를 함께 보고한다.
- 메시지 유무만의 효과는 이 실험으로 분리되지 않는다. 같은 분할에서 `send` 금지 조건이 별도로 필요하다.
