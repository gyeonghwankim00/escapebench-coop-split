# Solo 실험 프로토콜 v1

**이 문서는 이전 개발용 파일럿이다.** 원본 실험 설정을 따르는 현재 기준선은
[ORIGINAL_PROTOCOL.md](../../ORIGINAL_PROTOCOL.md)를 사용한다. v1의 temperature·출력·힌트·
이동 규칙은 원본과 다르므로 결과를 새 기준선과 합치지 않는다.

먼저 관찰·행동 인터페이스와 모델의 단독 퍼즐 해결 능력을 확인한다. Solo 자체가
진행되지 않으면 Peer 조건의 실패를 협업 능력 부족으로 해석할 수 없다.
기존 `run_model.py`/`run_solo_suite.py`와 이전 출력은 유지하며 새 실험은
`run_experiment.py`로 실행한다. 데이터 분할은 이번 변경에서 수정하지 않았다.

## 비교 설계

기본 [실험 설정](../../solo_pilot.json)은 기존 실행에서 반복 행동이 관찰된 02·06번을
사용한 개발용 진단이다. 이 선택은 사후 선택이므로 전체 EscapeBench의 성능을
대표하는 평가로 주장하지 않는다. 먼저 8B에서 인터페이스를 확인한 후 같은 계획을
14B로 실행한다. 모델 변경과 프롬프트·기억 정책 변경을 동시에 하지 않는다.

| 조건 | Qwen3 thinking | 50턴 연속 무진행 후 |
|---|---|---|
| direct_nohint | 끔 | 종료, 독립 수행 진행률 기록 |
| direct_hint50 | 끔 | 외부 힌트 제공 후 계속 |
| thinking_nohint | 켬 | 종료, 독립 수행 진행률 기록 |
| thinking_hint50 | 켬 | 외부 힌트 제공 후 계속 |

모든 조건은 같은 시스템 지시문, 관찰 포맷, 최근 10턴의 위치·행동·피드백,
temperature 0.6/top-p 0.95/top-k 20, 출력 상한 2,048토큰을 사용한다.
thinking의 내부 추론도 출력 예산에 포함된다. 따라서 이는 **같은 토큰 상한에서의
비교**이며 thinking에 충분한 추론 예산을 줬다는 보장은 아니다. 출력 상한 도달률과
파싱 실패율도 함께 확인하고, 높다면 예산을 늘린 별도 실험으로 비교한다.
과거 관찰 전체·영구 메모는 제공하지 않는다. 시작점은 원본 시작 장면이다.

관찰은 엔진의 공개 `observe()` 결과만 텍스트로 바꾼다. 현재 대상 물체, 이동할
구역, 소지품을 구분하고 `input`은 행동 지시가 아닌 문자열 입력임을 설명한다.
평가용 정답·진행률·숨은 상태는 무힌트 프롬프트에 넣지 않는다. 추론 텍스트에
JSON이 있어도 실행하지 않고 thinking 종료 후의 최종 JSON 하나만 실행한다.

기본은 2문제 × 4조건 × seed 42 = **8회**다. 파이프라인 확인 후
`--seeds 42 43 44`를 쓰면 24회다. 각 조건 시작 시 같은 seed로 난수를 초기화한다.
같은 문제의 반복 seed는 독립된 문제 표본이 아니므로 24문제처럼 해석하지 않는다.
모델 하나를 GPU에 한 번 올려 모든 실행을 순차 처리한다.

## 진행률과 힌트

진행률은 원본 상태 전이의 조건 충족과 도구 최초 획득을 고유 ID로 세어 계산한다.
반복 클릭·이동·실패·대기는 진행률을 늘리지 않는다. 복합 잠금의 각 조건은 별도로
계산한다. 8문제의 전체 분모는 순서대로 40, 38, 45, 46, 66, 57, 59, 48이다.
04·07은 한 행동이 조건 해결과 도구 생성을 함께 일으켜 정답 로그 행 수보다 1 크다.
정답 문자열과 행동이 일치하는지만 세던 이전 `reference_action_match_fraction`과
같은 지표가 아니다. 원본 평가 지표와의 완전한 수치 동등성도 주장하지 않는다.

주 지표는 첫 힌트 직전 진행률(힌트가 없으면 종료 진행률)이다. 함께 기록하는 것은
첫 정체 시점, 최종 진행률, 탈출 여부, 힌트 수, 잘못된 행동·파싱 오류·반복 행동,
입출력 토큰 수, 시간, GPU 최대 메모리다. 시간·턴 상한이 첫 정체나 탈출보다 먼저
오면 `censored`로 표시해 무진행 종료와 구분한다. 모델 오류나 외부 중단은 평균에서
제외하며 `Evaluated/planned`를 함께 표시한다. 원시 종료 사유는 `results.json`에 남는다.

힌트 조건에서는 새로운 진전 없이 50행동을 사용하면 **다음 턴부터** 아직 완료하지
않은 실행 가능한 정답 행동 하나의 장소와 행동을 알려준다. 힌트 선정은 복사한
환경에서 검사한다. 실제 환경에서는 모델이 직접 이동·행동해야 하며 순간이동이나
정답 강제 실행은 없다. 힌트는 해당 목표를 완료할 때까지 남고 20행동 동안 못 하면
`hint_following_failed`로 종료한다. 이후 새로운 50행동 정체 시 다음 힌트를 제공한다.

이는 [EscapeBench 논문](https://arxiv.org/html/2412.13549v2)의 정체·힌트 개념을
참고한 별도 프로토콜이다. 기존 엔진의 도달 가능한 구역 간 이동 압축을 유지하며,
원본 공개 구현의 도움 시 위치 변경·정답 강제 실행을 재현하지 않는다. 원본 논문의
성능 수치와 직접 비교하지 않는다. 협업 실패 단계 분류와 Peer/Oracle 비교는 아직
이 러너의 범위가 아니며, Solo 바닥 효과를 확인한 뒤 설계한다.

## 실행

로컬에서 모델 없이 계획과 2문제 정답 경로를 검증하고 초기 프롬프트를 저장한다.

```bash
python3 -m scripts.run_experiment --dry-run
bash server/upload.sh
```

서버에서는 이미 받은 모델과 기존 `.conda-env`를 재사용한다.

```bash
cd ~/escape-lab
sbatch server/experiment.sbatch
# 반복 실험은 기본 파일럿을 확인한 뒤 별도로 제출
# sbatch server/experiment.sbatch --seeds 42 43 44
```

로그는 `experiment-JOBID.out/.err`, 결과는 `outputs/experiment-시각/`에 생긴다.
`report.md`가 요약 표이고 `results.json`/`aggregate.json`이 원본 집계다. 각 문제의
`조건/seed-번호/attempt-번호/` 아래에 실제 메시지·출력·행동이 있는 `turns.jsonl`,
환경 이벤트 `events.jsonl`, `summary.json`, 설정과 GPU 메모리 기록이 저장된다.

Slurm 최대 시간은 **11시간 30분**, 러너 자체는 모델 로딩 포함 **10시간**, 에피소드별
최대 **30분 또는 1,000행동**이다. 기본 8회는 에피소드 예산 합계 4시간이고 실제 소요는
서버에서 측정해야 한다. 3 seed 24회는 최대 12시간이므로 한 작업 안에 끝나지 않을 수
있다. 전체 시간 상한에 걸린 실행은 아래 재제출로 이어간다. 설치·로딩 중 강제 종료까지
완벽히 막을 수는 없으므로 Slurm의 11시간 30분 상한이 마지막 제한이다.

```bash
# 최초 실행과 같은 모델·계획·seed 옵션을 함께 사용
sbatch server/experiment.sbatch --resume outputs/experiment-실제시각
```

완료된 에피소드는 건너뛰고 외부 중단·요약 없는 에피소드는 같은 seed로 처음부터
다시 실행해 새 attempt에 기록한다. **중간 게임 상태부터 복원하는 기능은 아니다.**
에피소드 자체의 시간 초과는 완료된 제한 실험으로 취급한다. 코드·데이터·설정이
바뀌면 재개를 거부하므로 새로운 출력 디렉터리에서 시작한다. 소스/데이터/프롬프트
해시, 패키지 버전과 모델 revision을 남긴다. 로컬 가중치는 크기·수정 시각만 비교하며
가중치 전체 내용 해시는 계산하지 않는다.

14B 모델이 서버에 준비되어 있으면 `--model /실제/모델/경로`만 바꿔 같은 실험을
제출할 수 있다. 현재 로더는 단일 GPU NF4 4비트이며, 14B의 실제 메모리 여유와 처리량은
직접 확인해야 한다. 32B용 다중 GPU 분산 로더는 구현하지 않았다.
